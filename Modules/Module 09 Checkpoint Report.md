# 7. Common Mistakes Pattern

```text
- Периодические синтаксические ошибки в SQL (порядок параметров, порядок ключевых слов).
- Использование `and` вместо `or` в условиях валидации нескольких полей.
- Сравнение значений с неправильным типом в тестовых утверждениях.
- Непоследовательные имена переменных (`result`, `res`, `r`) из-за раздражения от автодополнения.
- Возврат неправильного статус-кода для типа операции (201 вместо 200 для обновления).
- Попытка использовать модели данных для параметров, которые не находятся в теле запроса.
- Пропуск проверки на пустой список при возврате коллекций.
```

Эти ошибки не являются концептуальными. Они указывают на нестабильную синтаксическую беглость и требуют регулярной практики, а не изменения подхода к обучению. Наиболее критичная из них — путаница в семантике статус-кодов, поскольку это влияет на клиентский опыт и отладку.

# 14. Student Reflection

*(Эта секция заполняется студентом)*

**Какие концепции стали яснее?**

> Стало понятно, какими методами приложение может общаться с внешней средой, например, с сервером базы данных, и не только. 

**Что остаётся непонятным?**

> Поскольку в моей текущей версии проекта используется синхронная база данных SQLite3, я думаю, что мне не очень хорошо удалось освоить async/await, потому что я не применил его в своем реальном проекте, только в учебном. 

**Что было самой трудной частью?**

> Пожалуй, труднее всего было понять, как правильно использовать WebAPI и как связать его с остальной программой. Я не сразу понял, что HTTP запрос выражает намерение пользователя, и это намерение обрабатывается программой.

**Что хотелось бы исследовать дальше?**

> Я столкнулся с проблемой того, что текущая версия моего проекта сочетает в себе клиентскую и серверную части. У меня есть ядро, бизнес-логика проекта, которая отвечает за выполнение запросов, изменения в базе данных и прочее. И есть API/CLI Presentation Layer, который сейчас связан с остальной программой. В идеале было бы разделить это все на части. Серверная часть будет отвечать за бизнес-логику и вычисления, а приложение для ПК и сайт будут точками входа в бизнес-логику. 

> Также хочется перейти с простой базы данных SQLite3 на что-то более "взрослое", например, на PostgreSQL. Там я смогу, во-первых, в полной мере понять принципы async/await, а во-вторых, у меня появится две ветки приложения: серверная и клиентская. 

> Я не знаю, действительно ли уже пришло время для такого разделения, но чувствую, что потребность в этом точно есть. Потому что сейчас у меня есть API Endpoint'ы, но я по-сути никак их не использую в текущей реализации проекта.
