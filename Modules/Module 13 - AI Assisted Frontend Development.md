# APMF — Module 13

# AI-Assisted Frontend Development & Backend Integration

**Проект:** QR Warehouse  
**Предшествующий модуль:** Module 12 — PostgreSQL, Async Persistence & Database Migration  
**Основной результат:** первое рабочее браузерное приложение QR Warehouse, использующее существующий FastAPI backend.

---

## 1. Назначение модуля

В предыдущих модулях основное внимание уделялось серверной части QR Warehouse: модели предметной области, PostgreSQL, репозиториям, UseCases, API, транзакциям и миграциям.

Теперь проекту нужен пользовательский интерфейс, через который менеджер сможет работать с каталогом оборудования и сметами, не обращаясь напрямую к API.

Цель Module 13 — не подготовить студента к профессии frontend-разработчика. Цель — научиться организовывать разработку клиентской части с помощью AI-инструментов, понимать её устройство на достаточном уровне, контролировать качество сгенерированного кода и правильно интегрировать frontend с backend.

Основной принцип:

> ИИ может реализовывать большую часть визуального интерфейса и повторяющихся frontend-компонентов. Студент остаётся ответственным за требования, границы архитектуры, API-контракты, бизнес-сценарии, интеграцию и проверку результата.

Module 13 должен также помочь выявить недостающие возможности backend. Например, отсутствие поиска, фильтрации и пагинации может стать очевидным при создании каталога оборудования. В таких случаях мы будем расширять backend осознанно, а не имитировать необходимое поведение на клиенте.

## 2. Предполагаемый технологический стек

Это исходная рекомендация для модуля, а не требование использовать каждую библиотеку любой ценой. Перед началом реализации нужно проверить совместимость выбранных версий и зафиксировать окончательный стек.

| Область | Предлагаемая технология | Причина выбора |
|---|---|---|
| UI framework | React | Компонентная модель подходит для интерфейса с каталогами, формами, таблицами и карточками заказов; AI-инструменты хорошо поддерживают этот стек. |
| Language | TypeScript | Позволяет проверять типы запросов и ответов API, уменьшает число ошибок при интеграции. Требуется освоить только необходимый минимум. |
| Dev server / build tool | Vite | Простая настройка и быстрый цикл разработки; поддерживает шаблон React + TypeScript. |
| UI component library | Mantine — основной кандидат | Готовые формы, поля ввода, модальные окна, компоненты навигации, даты и уведомления позволяют не писать большую часть визуальных элементов вручную. |
| API schema | OpenAPI, генерируемая FastAPI | Один источник описания endpoint-ов, параметров, схем запросов и ответов. |
| Typed API access | openapi-typescript + openapi-fetch — кандидат | Типы TypeScript генерируются из OpenAPI, а запросы проверяются относительно API-схемы. |
| Package manager | npm | Достаточно для одного frontend-приложения; не требуется вводить сложную систему workspace без необходимости. |

### Почему React + TypeScript + Vite

QR Warehouse — внутреннее рабочее приложение, а не публичный контентный сайт, для которого важны поисковая индексация и серверный рендеринг каждой страницы. На первом этапе нет очевидной необходимости усложнять архитектуру Next.js или другими SSR-решениями.

React позволяет строить интерфейс из небольших переиспользуемых компонентов. TypeScript полезен как дополнительная проверка соответствия frontend и backend. Vite обеспечивает отдельный frontend dev server и production-сборку.

### Почему библиотека компонентов

Не планируется вручную разрабатывать собственную систему кнопок, форм, таблиц, модальных окон и уведомлений. ИИ должен использовать готовые компоненты, а не создавать самодельные аналоги без веской причины.

Mantine предлагается как отправная точка. На этапе проектирования можно сравнить его с альтернативами, но после выбора библиотеки не следует без необходимости смешивать несколько UI-систем.

Визуальное направление интерфейса: сдержанный тёмный графитовый стиль с приглушёнными синими акцентами, ясная иерархия, минимум визуального шума. Интерфейс должен быть прежде всего рабочим инструментом, а не демонстрацией эффектов.

## 3. Организация репозитория

### Рекомендация: monorepo

Для текущего масштаба QR Warehouse рекомендуется сохранить backend и frontend в одном Git-репозитории, но разместить их в отдельных каталогах.

Не следует использовать отдельные постоянные ветки `frontend` и `backend`. Git-ветки должны представлять отдельные изменения или задачи, а не части приложения.

Пример целевой структуры:

```text
QR-Warehouse/
├── backend/                    # серверная часть (если уже находится в корне,
│   ├── app/                    # не переносить её только ради красивого дерева)
│   ├── migrations/
│   ├── tests/                  # если/когда тесты будут восстановлены
│   └── ...
│
├── frontend/
│   ├── package.json
│   ├── package-lock.json
│   ├── index.html
│   ├── vite.config.ts
│   ├── tsconfig.json
│   └── src/
│       ├── app/                # запуск приложения, маршрутизация, providers
│       ├── pages/              # страницы
│       ├── features/           # функциональные области: equipment, estimates
│       ├── components/         # общие UI-компоненты
│       ├── api/                # API client и сгенерированные типы
│       └── styles/             # глобальные стили и тема
│
├── docs/
│   ├── architecture/
│   ├── workflows/
│   ├── api/
│   └── frontend/
│
├── compose.yaml
├── README.md
└── ...
```

Структура иллюстративная. Перед изменением каталогов нужно посмотреть на фактическое дерево текущего backend. Если серверная часть сейчас расположена в корне репозитория, на первом этапе достаточно добавить рядом каталог `frontend/`. Большое перемещение существующего backend в `backend/` не должно становиться побочной задачей Module 13.

### Почему один репозиторий лучше сейчас

- Один разработчик и один продукт.
- Frontend и backend меняются в рамках одного пользовательского сценария.
- Изменения API и соответствующего интерфейса можно просматривать в одном pull request.
- Общая документация и история решений находятся рядом с кодом.
- Не нужно синхронизировать два репозитория и отдельно выяснять, какая версия API совместима с какой версией клиента.
- Можно запускать backend и frontend отдельными процессами, сохраняя независимые зависимости и команды сборки.

Один репозиторий не означает, что frontend и backend становятся одним приложением или используют одну систему зависимостей. Python-зависимости остаются на стороне backend, npm-зависимости — внутри `frontend/`.

### Когда стоит разделить репозитории

Отдельные репозитории могут быть оправданы позже, если frontend и backend будут разрабатываться разными командами, выпускаться независимо, иметь разные права доступа или обслуживать несколько разных клиентов. Тогда понадобится формализованная публикация и версионирование API-контракта.

Пока таких требований нет, разделение создаст больше организационной работы, чем пользы.

### Ветки Git

Использовать обычные feature-ветки по задачам:

```text
feature/frontend-shell
feature/equipment-catalog
feature/catalog-search-api
feature/estimate-list
feature/estimate-builder
```

Если одна функция требует изменений в обеих частях приложения, соответствующие изменения можно держать в одной feature-ветке. Backend и frontend не обязаны разрабатываться в разных ветках.

## 4. Как frontend будет понимать API без постоянного переключения между кодом

Это одна из центральных тем Module 13.

### 4.1 OpenAPI как контракт

FastAPI автоматически генерирует OpenAPI-схему приложения. В стандартной конфигурации её можно открыть по адресу `/openapi.json`, а интерактивную документацию — через `/docs` (Swagger UI) и `/redoc` (ReDoc).

OpenAPI описывает доступные пути, HTTP-методы, параметры, тела запросов и схемы ответов. Поэтому frontend-разработчику не нужно каждый раз читать реализацию endpoint-а в Python, чтобы узнать ожидаемый формат данных.

Важно: OpenAPI описывает HTTP-контракт, но не заменяет объяснение бизнес-правил. Например, схема может показать статус ответа, но не всегда объяснит, почему менеджер не может подтвердить конкретную смету. Для этого нужны понятные описания endpoint-ов и документация пользовательских процессов.

### 4.2 Генерация TypeScript-типов

Предлагаемый процесс:

1. Запустить FastAPI в локальной среде.
2. Получить его OpenAPI-схему.
3. Сгенерировать TypeScript-типы в `frontend/src/api/`.
4. Использовать типизированный API client в компонентах frontend.
5. При изменении backend API обновить схему и повторно сгенерировать типы.

`openapi-typescript` генерирует TypeScript-типы из OpenAPI. `openapi-fetch` может использовать эти типы, чтобы проверять пути, параметры, тела запросов и ответы.

Примерная команда генерации будет настроена в npm scripts, а не запоминаться вручную. Конкретный URL и путь выходного файла будут определены после проверки backend.

Сгенерированный файл нельзя редактировать вручную: он является производным артефактом OpenAPI-схемы.

### 4.3 Где смотреть ответы endpoint-ов

Для ежедневной работы будут доступны три удобных способа:

- `http://localhost:8000/docs` — интерактивная документация и возможность отправить пробный запрос.
- `http://localhost:8000/openapi.json` — машинно-читаемая схема для генерации типов и инструментов.
- Сгенерированные TypeScript-типы и единый API client внутри frontend — для просмотра контрактов прямо в редакторе кода.

Таким образом, не придётся постоянно переходить в Python-код и искать response model. Однако при неясном бизнес-поведении всё равно нужно будет обратиться к UseCase и документации процесса.

### 4.4 Кто отвечает за контракт

Backend определяет фактический API-контракт. Frontend использует его, а не придумывает собственные несовместимые структуры.

Если интерфейсу не хватает поля или endpoint-а:

1. описать, какая пользовательская задача требует этих данных;
2. выяснить, есть ли они в текущем backend;
3. решить, нужно ли расширить API;
4. обновить backend и его OpenAPI-схему;
5. перегенерировать типы frontend;
6. подключить новый контракт в интерфейсе.

Не следует хранить вручную две независимые копии одной и той же схемы API.

## 5. Темы и учебные фазы

### Phase 0 — Product workflow & frontend scope

**Задача:** определить, какие рабочие процессы должен поддерживать первый интерфейс и какие роли будут им пользоваться.

Темы:
- пользовательский сценарий и его шаги;
- отличие страницы от бизнес-функции;
- основные состояния страницы: загрузка, успех, ошибка, пустой результат;
- определение границ первой версии;
- базовые принципы UX для внутреннего рабочего приложения.

Практика по QR Warehouse:
- составить карту страниц менеджера;
- описать работу с каталогом оборудования;
- описать просмотр списка смет;
- описать создание черновика сметы и добавление позиций;
- определить, какие сценарии уже поддерживает backend, а какие потребуют изменений.

**Результат:** карта интерфейса и список пользовательских сценариев с привязкой к существующим endpoint-ам.

### Phase 1 — Frontend project foundation

**Задача:** создать самостоятельное frontend-приложение внутри общего репозитория.

Темы:
- Node.js и npm на уровне запуска проекта и управления зависимостями;
- React и TypeScript template в Vite;
- dev server и production build;
- структура исходного кода;
- переменные окружения;
- разделение конфигурации разработки и production.

Минимальный теоретический минимум:
- что такое HTML-документ и семантическая разметка;
- что такое CSS и базовые способы компоновки;
- JavaScript как язык выполнения frontend-кода;
- TypeScript как статическая проверка типов.

Не требуется изучать HTML/CSS/JavaScript как отдельную профессию. Нужно понимать достаточно, чтобы читать код, задавать ИИ точные вопросы и замечать опасные изменения.

Практика по QR Warehouse:
- создать приложение;
- подключить библиотеку UI-компонентов;
- настроить базовую тему;
- сделать каркас приложения с навигацией и рабочей областью.

**Результат:** приложение запускается локально независимо от backend и имеет согласованный визуальный каркас.

### Phase 2 — React essentials for code review

**Задача:** освоить модель React настолько, чтобы контролировать сгенерированный код.

Темы:
- компонент;
- props;
- state;
- события и обработчики;
- отображение списков;
- условное отображение;
- формы и управляемые поля;
- эффекты и загрузка данных;
- маршрутизация между страницами.

Практика:
- создать навигационную оболочку;
- добавить несколько страниц;
- сделать статическую таблицу каталога;
- добавить форму и модальное окно.

**Результат:** студент понимает, где находится логика компонента, откуда поступают данные и что вызывает обновление интерфейса.

### Phase 3 — UI components, visual system & AI workflow

**Задача:** научиться поручать ИИ визуальную реализацию, сохраняя единообразие приложения.

Темы:
- использование библиотеки готовых UI-компонентов;
- тема, цвета, типографика и spacing;
- переиспользуемые компоненты;
- таблицы, формы, date pickers, модальные окна, уведомления;
- правила для AI coding agent;
- разбиение больших задач на небольшие изменения;
- просмотр diff перед принятием изменений.

Практика:
- зафиксировать визуальные правила QR Warehouse;
- создать общие элементы интерфейса;
- поручить ИИ собрать страницу каталога по согласованному описанию;
- провести ревью кода и исправить нарушения архитектурных правил.

**Результат:** ИИ способен ускорять создание интерфейса, не превращая каждый экран в визуально и технически отдельное приложение.

### Phase 4 — API contract & typed integration

**Задача:** подключить frontend к существующему FastAPI backend и сделать API-контракт доступным прямо из frontend-проекта.

Темы:
- HTTP-методы, URL, query parameters и request body;
- JSON и HTTP status codes;
- OpenAPI и автоматические документы FastAPI;
- генерация TypeScript-типов;
- единая точка настройки API client;
- обработка 2xx, 4xx и 5xx ответов;
- CORS и dev proxy;
- переменные окружения и адрес backend.

Практика:
- открыть `/docs` и `/openapi.json`;
- сгенерировать API-типы;
- создать единый API client;
- получить каталог из PostgreSQL через backend;
- отобразить реальные данные в браузере;
- корректно обработать сетевую ошибку и ошибку API.

**Результат:** frontend не использует фиктивные данные для основного рабочего сценария и получает информацию через существующий API.

### Phase 5 — Data-driven screens: search, filters & pagination

**Задача:** сделать каталог и список смет пригодными для повседневной работы.

Темы:
- загрузка и отображение серверных данных;
- состояние загрузки;
- пустые состояния;
- поиск;
- фильтрация;
- сортировка;
- пагинация;
- задержка отправки поискового запроса (debounce), если она нужна;
- сохранение фильтров в URL, если это оправдано.

Практика по QR Warehouse:
- поиск оборудования по названию и SKU;
- фильтрация по категории и типу учёта;
- список смет с фильтрами по статусу;
- постраничная загрузка данных.

Если backend пока возвращает полный список оборудования или смет, мы оценим, достаточно ли этого для прототипа. Для реального каталога поиск, фильтрацию и пагинацию предпочтительно реализовывать на сервере, чтобы не загружать весь набор данных в браузер.

**Результат:** менеджер может найти необходимую модель оборудования и нужную смету без просмотра длинных неструктурированных списков.

### Phase 6 — Estimate workflow: first vertical slice

**Задача:** реализовать первый законченный пользовательский процесс от страницы до базы данных.

Темы:
- формы создания и редактирования;
- клиентская валидация как дополнение к серверной;
- согласование полей формы с API-схемой;
- отправка команд на backend;
- отображение результата операции;
- предотвращение повторной отправки;
- ошибки бизнес-правил и обратная связь пользователю.

Практика по QR Warehouse:
- открыть список смет;
- создать черновик;
- открыть его детали;
- добавить и удалить позиции;
- отобразить количество и снимки данных позиции;
- отправить смету на следующий этап её жизненного цикла;
- показать понятное сообщение, если backend отклонил операцию.

Набор операций будет уточнён после проверки фактических endpoint-ов Module 12. Нельзя придумывать frontend-поведение, которое противоречит текущей бизнес-логике.

**Результат:** первый сквозной сценарий менеджера работает через браузер и существующий backend.

### Phase 7 — Manual acceptance, type checking & integration review

**Задача:** убедиться, что интерфейс работает не только в удачном сценарии.

Темы:
- ручные acceptance-сценарии;
- проверка состояний загрузки, пустых результатов и ошибок;
- проверка типизации TypeScript;
- production build;
- проверка API-контрактов;
- просмотр diff и возврат неудачных изменений;
- базовые браузерные инструменты разработчика.

Не предполагается строить большую систему frontend-тестирования в рамках первого модуля. Однако ручные сценарии и проверка сборки обязательны. TypeScript type-checking не заменяет runtime-тесты, но помогает выявлять несоответствия типов до выполнения приложения.

**Результат:** воспроизводимый сценарий проверки интерфейса и успешная сборка frontend.

|---|---|
| Dashboard / Overview | Краткая сводка и переход к основным разделам; сложная аналитика не требуется. |
| Equipment catalog | Просмотр, поиск и фильтрация моделей оборудования. |
| Estimates | Список смет, их статусы и поиск. |
| Estimate details | Просмотр позиций и основных сведений о смете. |
| Create estimate | Создание черновика и добавление оборудования. |

Приоритет — не число страниц, а законченный пользовательский сценарий. Если часть страниц не поддерживается существующим API, нужно явно зафиксировать это, а не маскировать незавершённость фиктивными данными.

## 7. Архитектурные правила Module 13

1. Backend остаётся источником истины для бизнес-правил, доступности оборудования, статусов и транзакций.
2. Frontend не подключается напрямую к PostgreSQL.
3. Frontend не дублирует бизнес-логику UseCases.
4. API-контракт определяется backend и публикуется через OpenAPI.
5. Сгенерированные API-типы не редактируются вручную.
6. UI-компоненты переиспользуются; не нужно создавать новый вариант кнопки или поля для каждой страницы.
7. ИИ не должен менять backend без отдельного объяснения причины и согласования изменения API.
8. Большие изменения разбиваются на небольшие задачи, результаты проверяются через Git diff.
9. Секреты, пароли БД и приватные ключи не помещаются в frontend. Любые переменные сборки, доступные браузеру, считаются публичными.
10. До реализации аутентификации и авторизации нельзя открывать приложение в публичный доступ с реальными данными склада.

## 8. Организация повседневной работы

Цель — избежать постоянного переключения между Python-кодом и frontend только для того, чтобы понять API.

### Основные источники информации

| Вопрос | Где смотреть |
|---|---|
| Какие endpoint-ы доступны? | FastAPI `/docs` или OpenAPI schema |
| Какой формат запроса и ответа? | `/docs`, сгенерированные TypeScript-типы, response models backend |
| Какую бизнес-операцию выполняет endpoint? | Документация workflow и соответствующий UseCase |
| Как frontend вызывает API? | Единый API client в `frontend/src/api/` |
| Какие страницы и сценарии существуют? | `docs/workflows/` и `docs/frontend/` |
| Какие правила соблюдать при генерации кода? | Короткий frontend AI guidance document |

### Документы, которые нужно поддерживать

- `docs/workflows/` — пользовательские процессы и жизненные циклы.
- `docs/api/` — обзор API и нестандартные бизнес-оговорки; не ручная копия OpenAPI-схемы.
- `docs/frontend/` — карта страниц, структура frontend и принятые решения.
- `frontend/AGENTS.md` или эквивалентный файл инструкций — ограничения и соглашения для используемого AI coding agent, если он поддерживает такие файлы.
- Корневой `README.md` — единая инструкция запуска backend, frontend и зависимостей.

Не следует документировать каждую мелкую деталь. Документы должны помогать принять решение и быстро восстановить контекст, а не дублировать исходный код.

### Локальный цикл разработки

Типичный цикл будет выглядеть так:

1. Запустить PostgreSQL и backend через существующий Docker Compose.
2. Запустить frontend dev server из `frontend/`.
3. Открыть браузер и проверить страницу.
4. При необходимости посмотреть API в `/docs`.
5. Попросить ИИ реализовать небольшую UI-задачу по описанному сценарию и контракту.
6. Проверить Git diff, запустить приложение и пройти сценарий вручную.
7. Зафиксировать изменения в одной feature-ветке.

Позже можно добавить корневые команды или скрипты для запуска нескольких частей проекта одной командой. В начале достаточно прозрачного и понятного запуска каждого сервиса.

## 9. Что не входит в Module 13

Чтобы модуль не разросся без необходимости, следующие темы откладываются:

- полноценное изучение HTML, CSS, JavaScript или TypeScript как отдельной специализации;
- сложные frontend-анимации и кастомная графика;
- PySide6 и отдельное desktop-приложение для кладовщика;
- полноценная система аутентификации и ролей — отдельная последующая тема;
- полноценная production-публикация frontend за reverse proxy, если она требует отдельной инфраструктурной работы;
- сложная аналитика, диаграммы и отчёты;
- мобильное приложение;
- полная система frontend runtime-тестирования.

**Важное ограничение:** до появления авторизации и проверки прав доступа frontend можно использовать в локальной или контролируемой тестовой среде. Его нельзя считать безопасным для публичного размещения с реальными данными.

## 10. Критерии завершения модуля

Module 13 можно считать завершённым, когда:

- [ ] Frontend расположен в отдельном каталоге того же Git-репозитория.
- [ ] Выбранный стек и структура проекта задокументированы.
- [ ] Локально запускаются backend и frontend.
- [ ] Студент может объяснить назначение React-компонента, props и state на уровне используемого проекта.
- [ ] OpenAPI schema используется как источник API-контракта.
- [ ] TypeScript-типы генерируются из backend OpenAPI schema и не редактируются вручную.
- [ ] Frontend использует единый API client.
- [ ] Реальный каталог оборудования загружается из backend.
- [ ] Реализован поиск и/или фильтрация в согласованном объёме; если для этого потребовались изменения backend, они оформлены отдельно и документированы.
- [ ] Реализован как минимум один полный сценарий работы со сметой через браузер.
- [ ] Обрабатываются состояния загрузки, пустой результат и ошибки API.
- [ ] Production build проходит, TypeScript type-checking проходит.
- [ ] Студент способен объяснить поток данных от действия пользователя через frontend и API до UseCase и базы данных.
- [ ] Основные ограничения, незавершённые сценарии и следующие задачи зафиксированы.

Количество строк кода, число компонентов и визуальная сложность не являются критериями успеха.

## 11. Предлагаемый формат взаимодействия с AI

Для каждой значимой задачи студент сначала формулирует:

- пользовательскую цель;
- ожидаемое поведение;
- страницу или компонент, который нужно изменить;
- endpoint и ожидаемый API-контракт;
- состояния загрузки, успеха и ошибки;
- ограничения, которые ИИ не должен нарушать.

ИИ должен:

1. Кратко предложить план изменения.
2. Назвать файлы, которые собирается создать или изменить.
3. Не менять backend и API без отдельного согласования.
4. Использовать существующие UI-компоненты и API client.
5. Объяснять существенные архитектурные решения.
6. После реализации сообщить, как проверить результат.

Студент должен просматривать diff, запускать приложение и проверять не только визуальный результат, но и поведение с реальными данными.

## 12. Ожидаемые результаты обучения

По окончании модуля студент не обязан уметь самостоятельно написать сложный frontend с нуля.

Он должен уметь:

- ориентироваться в структуре React-приложения;
- читать базовый HTML/CSS/JavaScript/TypeScript, встречающийся в проекте;
- формулировать задачи для AI coding agent так, чтобы изменения были ограниченными и проверяемыми;
- понимать, как frontend получает и отправляет данные;
- использовать OpenAPI для восстановления API-контракта;
- распознавать несоответствия API и пользовательского интерфейса;
- контролировать границы между frontend и backend;
- самостоятельно диагностировать простые проблемы интеграции;
- реализовать и проверить полноценный пользовательский сценарий с помощью ИИ.

Главный результат — не знание React как такового, а способность управлять разработкой клиентской части продукта, сохраняя ответственность за его архитектуру и поведение.

## 13. Возможные направления после Module 13

После завершения модуля учебный план следует уточнить по результатам интеграции. Предварительные следующие направления:

- аутентификация, авторизация и роли пользователей;
- дальнейшее развитие бизнес-сценариев менеджера;
- рабочее место кладовщика и QR-сканирование;
- PySide6 как отдельный desktop-клиент, если для него подтвердится необходимость;
- интеграция с Telegram;
- улучшение эксплуатационной надёжности и production deployment.

Module 13 не должен заранее предполагать, что все эти задачи обязательно понадобятся. Приоритет определяется реальными потребностями QR Warehouse.
